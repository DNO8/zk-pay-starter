# 05 · Nullifiers and double-spend

Spending a note reveals `nullifierHash`, not the note. The contract stores
each spent `nullifierHash` in persistent storage. A second withdraw with the
same hash must fail.

The nullifier is private, so two deposits from the same person are not linked
on-chain by anything except timing, amount, and the anonymity set size.

Mind TTL: persistent entries need `extend_ttl` or they expire and the
nullifier can be reused.

## GAP-4

Record spent nullifiers in `Pool::withdraw` and reject duplicates. Named test:
`rejects_reused_nullifier`.

## Hints

<a id="hints"></a>

**Hint 1 — concept.** The nullifier set is the double-spend database. It must
live at least as long as the pool.

**Hint 2 — shape.**

```
key = DataKey::Nullifier(bytes32(nullifier_hash))
if storage.has(key) { return Err(NullifierUsed) }
storage.set(key, true)
extend_ttl(...)
```

Do this **after** the proof verifies, **before** paying.

**Hint 3 — near-code.** `DataKey::Nullifier(BytesN<32>)` is already declared.
Convert `U256` to `BytesN<32>` with `to_be_bytes`. The skeleton currently
returns `Error::TodoGap` for every withdraw — replace that once GAP-5 is
also in place. The test expects the first withdraw to succeed and the second
to return `NullifierUsed`.
